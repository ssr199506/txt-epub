# TXT→EPUB 三版本 · 性能数据系统分析与机理结论

> 分析对象：v1.0.0（纯 Python）/ v2.0.0（Rust 加速）/ v3.0.0（管道 + 批处理）
> 数据源：6 样本小测试（126 run，干净环境）+ 桌面「新建文件夹」全集（46 本 / ~400MB，417×2 原始行 + 18，并发环境）
> 本文对原始日志做了 run_id 去重复核，并修正了前版报告中一处对照错误（见 §6）。

---

|---|---|---|---|
| 6 样本 | S1 切章 + S2 完整转换 × 3 版本 × 6 本 × 3 重复；S3 批量(5 本)；A1 检测 | 126 run | 干净（单任务顺序执行） |

### 1.2 数据质量声明（清点中核实的问题）

1. **日志含重复行**：旧后台任务（不带 `--resume`）把已存在的 run_id 重跑了一遍，parse 601 行 / full 685 行中真实唯一 run 各 417 个。聚合按 run_id 去重后中位数与不去重几乎一致（偏差 <0.06s），结论稳健。
2. **warmup 混入统计**：`WARM-v1/v2/v3-02` 三条记录缺 `warmup` 字段，未被过滤，但不影响中位数。
3. **全集在并发负载下测得**：parse 与 full 两个场景同时跑、最多 3 个后台任务并行，wall_s 绝对值被环境噪声放大（尤其 v2 的进程+磁盘路径，parse_s 从干净环境的 0.78s 涨到 1.52s）；三版本同时受同等噪声，相对排序仍可靠。**全集绝对值只用于排序，不用于定量对比**。
4. **epub_valid 双行**：5 条 v3 失败记录每个 run_id 都有「False 先、True 后」两行，即同一本书被真实执行两次、一次失败一次成功——失败是真实的偶发现象，不是日志污染。

## 2. 三版本代码路径差异（机理基础）

| 环节 | v1 | v2 | v3 |
|---|---|---|---|
| 切章引擎 | Python `re` 逐行 | Rust fancy-regex（`parse_txt_rust.exe` 子进程） | Rust fancy-regex（子进程） |
| 数据搬运 | 直接 `open()` 逐行迭代 | 写 UTF-8 临时文件（磁盘）→ exe 读文件 → JSON 回传 | 内存解码 → stdin 管道喂 exe → JSON 回传 |
| 单本进程数 | 0 | 1 exe/本 | 1 exe/本（pipe）；批量 1 常驻（serve） |
| 批量能力 | 无（GUI 逐本转换） | 逐本子进程 | serve 常驻 + rayon 并行 + 帧协议 |
| 额外特性 | — | — | 编码自动检测、GBK/GB18030 raw 模式、卷嵌套 TOC |

关键代码事实（已核对源码）：

- **v2 的 Python 桥接写死了 `--source <路径>` 模式**（`txt_to_epub_core.py::parse_txt_index` 先 `mkstemp` 写 UTF-8 临时文件再调 exe），尽管 v2 的 Rust `main.rs` 其实支持 stdin——桥接层没走。
- **v3 的 `_index_with_rust_pipe` 走 stdin 零落盘**（`--mode parse` 不带 `--source`），并把 UTF-8 字节放在内存 `Utf8Buffer` 里供后续按偏移读正文。
- **v2/v3 的 Rust 匹配内核 `parse_chapters_with_re` 代码相同**（逐行 + `trim_start` 预筛 <80 字 + fancy-regex `match_at_start`）。两版本 Rust 差异仅在 v3 新增 serve 常驻、rayon 并行、encoding_rs raw 模式。
- **三版本 EPUB 打包全部用 ebooklib `epub.write_epub`**，无自定义 zip 写入；v3 多了卷嵌套 TOC 组装，不影响 zip 结构。

## 3. S1 切章：为什么 v1 的 Python 正则反而最快

数据：v1 0.25s / v3 0.96s / v2 1.52s（全集 parse_s 中位数）。

机理分解：

1. **v1 的解析成本天然很低**：`parse_txt` 对每行先做 `lstrip` + 长度 <80 的快速预筛，只有标题候选行才跑正则。8MB 文本约 6 万行，其中标题候选行只有几百行——Python 正则慢，但只在少数行上执行。整本纯解析约 0.25s。
2. **v2/v3 每次解析要付「进程启动 + 数据搬运」固定成本**：Windows 下启动一个 Rust exe（进程创建 + fancy-regex 编译 + serde_json 序列化 + 回传）约 0.4–0.5s，是纯解析本身的两倍。固定成本与文件大小无关。
3. **v2 比 v3 多付一次磁盘往返**：v2 写 8MB 临时文件再让 exe 读回 = 两次磁盘 IO + 一次杀软实时扫描窗口；v3 走 stdin 管道零落盘。全集并发环境下 v2 的磁盘路径被争抢进一步放大（0.78→1.52s）。

结论：在万行级 / 8MB 级文本上，「Rust 正则更快」的计算优势（微秒级）被「进程启动 + 搬运」（数百毫秒级）完全淹没。单本切章场景，Rust 无收益。

## 4. S2 完整转换：瓶颈根本不在切章

数据：v1 2.78s / v3 3.50s / v2 4.28s（全集 wall 中位数）。

机理分解：

1. **瓶颈是 EPUB 打包**：ebooklib `build_epub`（逐章生成 xhtml + `<p>` 段落组装）+ `write_epub`（zip 压缩）约 2.4–2.6s，占 wall 的 85–90%。
2. 切章时间（0.25s vs 0.96s）的差异在 2.8s 总量里只占约 10–20%——**加速切章对端到端几乎无感**。这是 v2/v3 在 S2 无法翻盘的根本原因：它们把精力花在整条链路占比最小的环节上。
3. v2 每本叠加 exe 启动 + temp 落盘 + 逐章 seek 读回，额外 +1.5s；v3 叠加 exe 启动 + 管道 + 内存解码，额外 +0.7s。v1 零额外开销，故最快。

## 5. 内存与进程行为

- 峰值 RSS 三版本 64–98MB，差异不大：v1 略高（Python 持有全文 + 章节字符串列表），v2/v3 因 exe 子进程持有部分数据相近。
- S1/S2 单本：v2/v3 各 1 个 exe 进程，v1 0 个。
- S3 批量进程数（并发观测，含噪声）：v2 sub 63 / v3 pipe 53 / v3 serve 4。serve 把「每文件一个进程」压到「一批一个进程」。

## 6. S3 批量：修正前版报告的对照错误

S3 场景**只做切章索引、不做 EPUB 打包**（`batch_parse_index` / `parse_txt_index` 只回传章节偏移，返回 `chapter_count`）。

前版报告写「v3 serve 15.9s 比 v1 逐本串行 ≈119s 快 7.5 倍」——**此对照不成立**：119s 是 v1 的 S2 完整转换（含打包）时间，而 S3 不含打包。正确的 v1 对照是纯切章串行：

| 模式 | 45 本切章时间 | 进程 | 说明 |
|---|---|---|---|
| v1 串行（估算） | **≈12.3s** | 0 | 45 × 0.274s（全集 v1 parse 中位数） |
| v3 serve（实测） | 15.9s | 4 | 1 常驻 + rayon 并行 + 帧协议 |
| v3 pipe（实测） | 47.5s | 53 | 每本启进程 + stdin 管道 |
| v2 sub（实测） | 90.1s | 63 | 每本启进程 + temp 落盘 |

修正后的结论：

1. **纯切章吞吐，v1 依然最快**（12.3s < 15.9s）。v3 serve 相对 v1 慢约 29%——v3 每本要付「Python 内存解码 + 帧管道 + JSON 序列化 + 线程池调度」约 0.35s，比 v1 的「流式读文件 + 逐行正则」0.27s 更贵。在这个量级，**数据搬运成本仍大于 Rust 正则加速收益**。
2. **v3 serve 的真实价值是相对 v2 的**：90.1/15.9 ≈ **5.7 倍**，来自消灭「每文件一次进程启动」（63 次 → 1 次）。这是 v3 管道架构相对 v2 的实质收益，前版报告的倍数应改为 5.7x 且对照对象是 v2，不是 v1。
3. v3 serve 相对 v1 的架构优势不在本数据集体现，而在「海量文件」场景：25 万文件时 v2 的启动开销约 25 万 × 0.4s ≈ 28 小时纯启动，serve 只启动 1 次；且 v1 没有批量索引 API（GUI 是逐本完整转换）。

## 7. epub_valid 偶发失败（v3，5/138 run）

现象：样本 10/22/27/33/46（体积 8.28–9.75MB，全集最大 5 本中的 5 本，含唯一 GB18030《吞噬星空》9.75MB）各出现 1 次 `epub_valid=False`；同一 run 二次执行即成功；v1/v2 在同样 138 run 上 100% 有效；全部失败发生在并发高负载时段（CPU 34–87%）。

机理判断（证据指向，非定论）：

- 校验逻辑是「`write_epub` 写完后立即 `zipfile.ZipFile` 打开检查 mimetype / META-INF」。失败即 zip 打开异常或关键成员缺失。
- 失败样本全部为最大体积文件：写 zip 耗时最长，被并发争抢 / 杀软实时扫描打断的窗口最宽。
- v1/v2 同场景零失败，v3 独有差异：管道模式在转换期间持有整本 UTF-8 内存副本（峰值压力更大），且 build_epub 走卷嵌套 TOC 组装路径。
- 结论：这是 v3 在「高负载 + 大文件」下的 zip 写入/校验竞态，非内容损坏（章数、体积均正确，重跑即恢复）。要定根因需对这 5 本做复现实验（连续多次 v3 转换 + 捕获 zipfile 异常详情），本次未做。

## 8. 结论

1. **三版本不是同一内核的调优，而是三个设计目标的产物**：
   - v1 为「单本交互」（GUI 双击转换）设计——零进程、零搬运，8MB 级文本切章 0.25s、端到端 2.8s。
   - v2 为「把长规则正则交给 fancy-regex」设计——但桥接层用临时文件搬运，付出进程 + 磁盘双重代价，是三者中最慢的过渡架构。
   - v3 为「25 万文件批量索引」设计——stdin 零落盘修掉 v2 的 IO 黑洞，serve 常驻 + rayon 消灭逐文件启动。
2. **在桌面这批 46 本 / 4.7–9.8MB 的书上，v1 全面最优**：单本切章、单本完整转换、45 本批量切章串行均胜出。v2/v3 不是「负优化」，而是为它们的目标场景（超大单文件、海量文件、编码自动检测）付了本数据集用不上的成本。
3. **v2/v3 追上 v1 的两个前提**（本数据集未达）：单文件超过约 45MB（v1/v2 线性模型持平点）让 Rust 计算优势盖过启动成本；或文件数到万级让 v3 serve 的常驻与并行摊薄搬运成本。
4. **v3 的管道架构在批量上有真实收益，但被前版报告高估**：相对 v2 快 5.7 倍是真，相对 v1「快 7.5 倍」是错误对照（见 §6）。v3 唯一在实测中超过 v1 的指标是「每文件 1 进程 → 一批 1 进程」的架构能力，以及编码自动检测（<0.08s，可忽略成本）。
5. 遗留问题：v3 大文件 epub 偶发校验失败需复现定位；S3 未测「批量 + 打包」的端到端吞吐，v3 serve + pack 模式在完整批量转换场景的真实优势未被本测试覆盖。
