# TXT→EPUB v3 · 后续改进方向：raw 模式解码改造（parity 红线解除路线图）

> 记录时间：2026-08-07
> 背景来源：三版本性能测试与机理分析（`性能数据系统分析.md`）
> 适用代码：v3（`versions/v3_current/`，上游仓库 `github-txt-epub_2026-07-25`）

---

## 1. 背景与目标

v3 存在两条吃数据的路径：

- **pipe/serve 模式（当前默认）**：Python 侧解码（`_decode_to_utf8_bytes`，语义 = `open(encoding, errors="ignore")`）→ UTF-8 字节经 stdin 喂 Rust，Rust 只切章。
- **raw 模式（`raw_offsets=True`，已实现未启用）**：Rust 用 `encoding_rs` 直接解码原始字节并切章。

现状问题：pipe/serve 的 Python 侧解码路径**不是瓶颈**（2026-08-08 实测修正，见下方「实测修正」段）——Python codec 极快（8MB 级 decode 仅 ~10ms），Python 侧读+decode+encode 合计约 30–55ms/本。启用 raw 的实测收益是省掉这段解码搬运（约 10–15%），但被 **parity 红线**挡住——红线要求"解码永远留 Python，Rust 绝不碰原始 GBK 字节"，以保证三版本输出逐字节一致（md5 一致是项目验收底线）。

**目标**：把 Python codec 的语义复刻进 Rust，使 raw 模式解码结果与 pipe 模式（进而与 v1）逐字节一致 → 安全默认启用 raw，省掉 Python 侧解码搬运。

## 2. 三个待修问题（parity 三坑）

| # | 问题 | 差异点 | 触发条件 |
|---|---|---|---|
| 1 | 非法字节处理 | Python `errors="ignore"` **丢弃**；encoding_rs 默认 **替换为 U+FFFD（�）** | 文件编码错标 / 拼接 TXT / 尾部乱码，含非法字节序列 |
| 2 | GBK 映射分叉 | Python gbk/gb18030 codec 用 GB18030 超集映射；encoding_rs 用自有表，生僻字/扩展区码位不一致 | GBK/GB18030 书含映射分歧码位 |
| 3 | 行尾对齐 | Python `open()` universal newline（`\r\n`/`\r` → `\n`）；raw 按原始字节流解码 | 含 Windows 换行（`\r\n`）的文件 |

后果：正文出现 � / 个别字不同 / 字节偏移漂移（偏移漂移最隐蔽——索引看着对、按偏移取正文错位）。

## 3. 修法、工程量、侵入性

### 3.1 修法 3：universal newline 归一化对齐（建议最先做）

**做法**：Rust 解码循环中做 `\r\n`/`\r` → `\n` 归一化，字节偏移基于归一化后的流；重点验证 `\r\n` 跨 8192 字节 chunk 边界的情形（`parse_chapters_raw` 已有 pending 对齐雏形，补全即可）。

**工程量：小。** 纯解码循环内部逻辑，无外部依赖。

**侵入性：低。**
- 改动面：仅 `rust/src/lib.rs`（`parse_chapters_raw` 内部）
- 接口：无变化（不新增/不修改参数）
- 行为：只影响 raw 模式输出（当前默认不启用），pipe 路径不受影响
- 回归风险：低；用含 `\r\n` 的文件对比 raw 与 pipe 的偏移/正文即可验证

### 3.2 修法 1：非法字节容错解码复刻（Python ignore 语义）

**做法**：基于 encoding_rs 底层 `Decoder` API 实现"出错处跳过最小非法字节数、继续解码"的循环，逐字节对齐 Python `errors="ignore"` 的规则；配套构造非法序列测试集（截断多字节、孤立续字节、非法首字节、超长序列等）与 Python 逐字节比对。

**工程量：中。** 主要成本在行为对齐与测试集构造，不在实现本身。

**侵入性：低–中。**
- 改动面：`rust/src/lib.rs`（新增容错解码函数）+ `rust/tests/`（或独立测试集脚本）
- 接口：无变化
- 行为：只影响 raw 模式；pipe 路径不动
- 回归风险：中——"与 Python 一致"需全量回归（见 §5 验收）；若对齐有偏差会重新引入字节级差异

### 3.3 修法 2：GBK/GB18030 映射表统一（diff + 补丁覆盖层）

**做法**：对 Python gbk/gb18030 codec 与 encoding_rs 做全码位映射 diff，把**差异码位**生成补丁覆盖表（预计数千级别，几 MB 以内），Rust 解码时查表采用 Python 语义；diff 与表生成各做一次，之后可固化。

**工程量：中–大。** 一次性成本集中在 diff 工具、表生成、全量验证；后续维护成本低。

**侵入性：低。**
- 改动面：新增映射表数据文件 + `rust/src/lib.rs` 解码查表逻辑
- 接口：无变化
- 行为：只影响 raw 模式下 GBK/GB18030 文件的解码结果；UTF-8 不受影响（无分叉）
- 回归风险：中——表数据需入库（体积、来源可追溯），且要覆盖全部差异码位才算闭环
- 注意：Python 侧 codec 若随版本升级换表，需重跑 diff 核对（低概率，记录在案即可）

## 4. 前置/更高价值项：坏字节检测上报（建议与 3.1 同期做）

**动机**：即使三坑全修，也只是复刻了 Python `errors="ignore"` 的"默默丢字节"语义——读者看到少字且永远不知道书坏了。更有价值的工程是**让错误可见、可控制**：解码时统计非法字节（所在文件、位置、数量），随结果返回并展示，提示用户该书存在编码问题；用户可选"按 ignore 丢 / 按 U+FFFD 替换 / 修书"。

**工程量：小–中。** 统计逻辑简单；工作量在结果数据结构扩展与下游展示。

**侵入性：中。**
- 改动面：Rust 结果 JSON 新增字段（如 `encoding_issues: [{offset, bytes_skipped}]`）+ Python 侧 `parse_txt_index` 返回值透传 + GUI/CLI 展示
- 接口：**向后兼容**（新增字段，不删不改旧字段），但消费方需感知新字段
- 行为：不改现有输出内容，只增加信息
- 回归风险：低

**独立价值**：即使不做 raw 提速，该功能也值得单独上线——把 v1 时代"无知的宽容"升级为"知情的宽容"，是 v3 在正确性上超越 v1 的点。

## 5. 验收方式（所有修法共用）

1. **单测**：对 §3 各测试集断言 raw 输出与 pipe 输出逐字节一致（偏移 + 正文）。
2. **全量回归**：46 本全集（45 UTF-8 + 1 GB18030）用 raw 与 pipe 各跑一遍，比对章数、正文 md5、EPUB 体积——三坑修完后应 100% 一致。
3. **性能确认**：raw 模式（含 serve-raw，需新写）实测吞吐相对 pipe/serve 的提升幅度——按 2026-08-08 实测锚点，预期 **10–15%**（见下方「实测修正」），确认改造收益兑现。若目标是海量文件吞吐，应把投入放在进程启动消除（serve 化）与帧协议精简上，收益更大。

## 6. 总体评估与建议顺序

| 项 | 工程量 | 侵入性 | 建议 |
|---|---|---|---|
| 3.1 行尾对齐 | 小 | 低 | 第 1 步 |
| 4 坏字节检测上报 | 小–中 | 中（接口扩展，向后兼容） | 与 3.1 同期，独立价值最高 |
| 3.2 ignore 复刻 | 中 | 低–中 | 第 2 步（需测试集） |
| 3.3 GBK 映射统一 | 中–大 | 低 | 第 3 步（一次性 diff） |

- **合计工程量：中–大，可分期投入**；前三步不互相依赖，任一步完成都能独立改善 raw 的可用性。
- **侵入性总体结论**：改动全部集中在 Rust 侧（`rust/src/lib.rs` + 表数据文件），Python 桥接层几乎不动，不改变现有接口契约；主要风险是行为一致性回归，而非结构性改动。
- 全部完成后，parity 红线可安全放开：raw 默认启用 → v3 单本/批量路径省掉 Python 解码搬运（~10–15%）。**注意：这不足以让 v3 反超 v1**——单本场景 v3 的绝对大头是 exe 进程启动（~170ms/本），批量 serve 的大头是 Rust 切章 + 帧协议；v1 没有进程成本。要让 v3 在海量中小文件场景真正具备竞争力，需配合「serve 化单本调用 + serve-raw + 帧协议精简」的组合改造（见「实测修正」），单独修解码意义有限。

## 7. 实测修正（2026-08-08，合成 15.8MB / 9864 章，干净单机，主项目代码）

> 本段修正此前「Python 解码是 serve 瓶颈、raw 预期省 20–40%」的错误判断。

**实测锚点**：

| 环节 | 耗时 |
|---|---|
| 空进程启动（exe） | 171 ms |
| Python 读+decode+encode（15.8MB） | 55 ms |
| pipe 端到端（启动+搬运+Rust） | 317 ms = 171 + 55 + 137 |
| raw 端到端（启动+Rust 读+解码+切章） | 270 ms = 171 + 100 |
| **raw 净省** | **47 ms ≈ 15%** |

**结论**：
1. Python codec 极快（8MB 级 decode ~10ms），Python 侧解码搬运合计仅 30–55ms/本——**不是瓶颈**。
2. 单本场景（S1/S2）的绝对大头是 **exe 进程启动 ~171ms**（占 54%），raw 动不了它；S2 打包瓶颈下 raw 端到端省 ~1.5%，几乎无感。
3. serve 批量场景**没有 raw 变体**（serve 帧协议 = Python 传 UTF-8 文本帧，Python 解码绕不开），要省这段需新写 serve-raw（帧传路径+编码，Rust 自解码），估计省 30–55ms/本 ≈ 8–15%。
4. 若目标是海量 10MB 级小说吞吐，优先级应为：**进程启动消除（把单本调用也 serve 化）> serve-raw > 帧协议精简**，单独修解码收益有限。
