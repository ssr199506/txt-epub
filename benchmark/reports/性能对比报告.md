# TXT→EPUB 三版本性能对比测试报告

- 测试日期：2026-08-07
- 测试对象：`txt-epub` 三个版本快照 v1.0.0（纯 Python）/ v2.0.0（Rust 加速）/ v3.0.0（管道 / 批处理）
- 全部数据位于 `txt-epub-perf_2026-08-07/`，桌面源文件与 GitHub 仓库未改动

---

## 0. 结论速览

| 场景 | 结论 |
|------|------|
| S1 切章（单本） | v1 纯 Python 正则最快（parse_s 0.12–0.40s）；v2/v3 走 exe 子进程反而慢 2–4 倍（0.55–0.88s）。小样本下 Rust 计算优势被进程启动开销抵消 |
| S2 完整转换（端到端） | v1 最快（wall 1.95–4.00s），v2 最慢（2.90–5.66s），v3 居中（2.54–5.03s）。瓶颈在 EPUB 打包（ebooklib），切章占比小 |
| S3 批量（5 本一批） | v3 `--serve` 常驻模式 1.85s / 1 进程，比 v2 逐本子进程（3.69s / 5 进程）快约 2 倍、进程数降到 1。批量常驻是 v3 架构真正体现价值处 |
| A1 编码择优 | v3 检测耗时 <0.06s，代价可忽略 |
| 正确性 | 6 本 × 3 版本章数与标题序列完全一致（0 差异）；54 个 EPUB 产物全部有效，同本输出体积一致 |

一句话：Rust 内核在**单本/完整转换**上未带来收益（被 exe 启动与 EPUB 打包抵消）；其价值集中在 **v3 批量常驻（serve）** 模式。

---

## 1. 测试环境与公平性设计

**样本**
- 源：桌面「新建文件夹」46 本 TXT（4.8–9.7MB）。
- 选取 6 本复制到 `samples/` 设为只读副本（不碰源文件），编码构成：45 本 UTF-8 + 1 本 GB18030（《吞噬星空》）。
- 样本清单见 `probe/sample_manifest.json`（含 md5）。

**三版本独立物化**
- 用 `git archive` 把 v1.0.0 / v2.0.0 / v3.0.0 物化为 `versions/v1_pure_python`、`v2_rust_accel`、`v3_current` 三个独立目录。
- 原因：v2/v3 的 `_RUST_BIN` 是相对路径（要求 exe 与 `txt_to_epub_core.py` 同目录），且三版本有同名模块，放一起会互相覆盖 exe、import 冲突。

**Rust 单独编译（关键）**
- v2 的 `rust_src/` 仅有 `.rs` 源码、**无 Cargo.toml**（v3 才有完整工程）。按 v3 格式重建最小 `Cargo.toml`（仅声明编译目标与依赖 `fancy-regex 0.13` / `serde_json`，**不含** v2 没有的 `rayon` / `encoding_rs`，未改任何代码），一次编译通过，产物命名 `parse_txt_rust.exe` 放 v2 目录。
- v3 用自带 `rust/Cargo.toml` 编译，产物放 v3 目录。
- 两套 exe 是不同的二进制（v2 4.55MB / v3 5.22MB），绝不混用。

**统一运行时**
- 系统 Python 3.12.10（实测 `ebooklib` / `PIL` / `psutil` / `tkinterdnd2` 均可用）。

**排除干扰变量**
- 规则一致性：三版本 `exportTxtTocRule..json` 与内置 `TOC_RE` 的 md5 完全一致 → 规则差异变量排除。
- 乱序：126 个 run 全局 shuffle（固定 seed=20260807），warmup 保持最前，排除执行顺序干扰。
- 重复：每场景每样本 3 次，报告取中位数；原始值全保留于 `bench_raw.jsonl`。

## 2. S1 切章（隔离内核，decode 统一预读）

解码阶段三版本共用同一份预读（`decode_s`，约 0.01–0.05s）；`parse_s` 为各版本真实切章内核耗时。

| 版本 | 样本01 | 02 | 03 | 04 | 05 | 06 | parse_s 均值 |
|------|--------|----|----|----|----|----|--------------|
| v1   | 0.313  | 0.140 | 0.171 | 0.155 | 0.339 | 0.223 | **0.224** |
| v2   | 0.820  | 0.725 | 0.696 | 0.808 | 0.882 | 0.728 | **0.777** |
| v3   | 0.754  | 0.548 | 0.591 | 0.706 | 0.772 | 0.613 | **0.664** |

- v1 纯 Python 正则比 v2/v3 的 Rust 内核快约 **3–4 倍**。
- 原因：样本为万行级，Rust 内核计算优势（微秒级）被 exe 子进程启动（约 0.4s）+ 文本回传开销完全抵消。**单本切章场景 Rust 无收益**。

---

## 3. S2 完整转换（convert_single 端到端）

| 版本 | 样本01 | 02 | 03 | 04 | 05 | 06 | wall_s 均值 | epub_valid |
|------|--------|----|----|----|----|----|-------------|------------|
| v1   | 4.00 | 1.95 | 2.72 | 2.76 | 2.85 | 2.40 | **2.78** | 1.0 |
| v2   | 5.66 | 2.90 | 3.04 | 3.66 | 3.90 | 3.32 | **3.75** | 1.0 |
| v3   | 5.03 | 2.54 | 2.66 | 3.40 | 3.48 | 3.04 | **3.36** | 1.0 |

- v1 端到端最快，v2 反而最慢。
- 原因：瓶颈在 EPUB 打包（ebooklib，占 wall 70%+），切章只占小部分。v2 每本额外承担 exe 启动 + 数据回传开销，无法被 Rust 切章加速抵消，故 v2 比 v1 还慢。
- 三版本同一本输出体积一致（如样本01 均为 7376–7377 KB），转换结果等价。

---

## 4. S3 批量（5 本 UTF-8 一批）

| 模式 | 版本 | wall_s | 峰值MB | exe 进程数 |
|------|------|--------|--------|-----------|
| sub  | v2   | 3.69   | 71.5   | 5 |
| pipe | v3   | 3.50   | 84.5   | 5 |
| serve| v3   | **1.85** | 79.9 | **1** |

- v3 `--serve` 常驻模式比 v2 逐本子进程快约 **2 倍**，且 exe 进程数从 5 降到 1（避免反复启停开销与内存峰值叠加）。
- pipe 与 sub 接近（均逐本起进程）。
- **批量常驻是 v3 管道架构相比 v2 的实质性能收益所在**；单本/完整转换场景该收益不体现。

---

## 5. 附加观测

- **A1 编码择优**：v3 `detect_encoding` 中位数 <0.06s（UTF-8 近乎 0，GB18030 0.004–0.02s），可忽略。
- **内存**：峰值 RSS 70–100MB，v1 略高（Python 持有全文+章节列表），v2/v3 因 exe 持有部分数据相近。
- **exe 进程**：S1/S2 每本 1 个 exe；批量 sub/pipe 5 个；serve 仅 1 个常驻。

---

## 6. 正确性校验

- **章数一致**：6 本 × 3 版本章数完全相同（`titles_check.py` 以 v3 为基准比对标题序列，**0 处差异**）。
- **EPUB 有效**：54 个 S2 产物 `epub_valid=1.0`（含 `mimetype` 与 `META-INF/`）。
- **输出一致**：同本三版本输出 KB 一致。

## 7. 探针偏差修正记录

S1 初测时 v1 章数偏少（样本01/04/05 显示 1599/1013/907，真实为 1601/1014/910）。

**定位**：`bench_worker.py` 的 `run_parse` 对 v1 传了 `text_str=text`（一份 `errors="ignore"` 整文件预解码串）。v1 的 `parse_txt` 在该路径下用 `splitlines` 解析，因丢字节破坏部分行边界致少切 1–3 章；其原生 `open(encoding, errors="ignore")` 路径（S2 / `convert_single` 所用）正确。

**修正**：S1 对 v1 改走原生自解码路径（不传 `text_str`，与 S2 一致），删除 18 条偏差日志行后 `--resume` 重测。修正后 S1 三版本章数完全一致。

**影响说明**：v1 的 `parse_s` 因此含其自解码开销（约 0.04s）；`decode_s` 仍单列展示三版本等价（约 0.01–0.05s）。这不影响结论方向（v1 纯 Python 正则仍远快于 v2/v3 的 exe 路径）。

## 9. v2 重建假设说明

v2 的 `rust_src/` 仅有 `.rs` 源码、无 `Cargo.toml`（v3 才有完整工程）。为公平测 v2，按 v3 格式重建最小 `Cargo.toml`：仅声明编译目标与依赖 `fancy-regex` / `serde_json`，**未引入 v2 没有的 `rayon` / `encoding_rs`，未改动任何代码**，一次编译通过。

此假设的含义：v2 的"Rust 加速"指其原始 `.rs` 逻辑经标准 `cargo build` 后的性能，不含 v3 才有的并行（`rayon`）/常驻（`serve`）/ `encoding_rs` 优化。因此 v2 与 v3 的 Rust 内核是两套不同代码，性能差异反映各自历史实现，而非同一内核的调优。
