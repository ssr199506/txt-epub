# TXT → EPUB 转换工具（Rust 解析内核）

一个把纯文本小说（TXT）转换成 EPUB 电子书的桌面小工具：自动按章节切分、批量处理、编码自动检测、章节拖拽排序、封面裁剪。章节切分内核由 Rust 承担，架构面向大规模小说库（845 GB / 25 万文件）批处理场景。


## 功能

- **TXT → EPUB**：正则规则自动识别章节标题并切分正文
- **批量处理**：一次多本连续转换，支持单进程常驻批处理（`--serve`）
- **编码自动检测**：拖入即自动判定 utf-8 / gb18030 / big5（择优范式），可手动覆盖
- **编码实时预览**：转换前预览前 800 字，避免乱码
- **章节预览与排序**：列出识别出的章节，支持拖拽调整顺序
- **封面支持**：可选图片封面 + 裁剪预览
- **嵌套目录**：按「卷/部/篇/集 → 章」自动生成层级 TOC，O(n) 复杂度
- **Rust 内核加速**：章节匹配由 `parse_txt_rust.exe` 承担，比纯 Python 快数倍

## 快速开始

```bash
pip install EbookLib Pillow tkinterdnd2
python txt_to_epub_gui_2.py    # 或双击 run_gui.bat 一键启动
```

需要桌面图形环境（Tk）。GUI 启动时会自动检查缺失依赖并尝试安装。

使用流程：选择/拖入 TXT → 确认编码（自动检测，乱码可手动改）→ 检查章节（可拖拽排序）→（可选）加封面 → 转换生成 `.epub`。

## 设计思路

面向 845 GB / 25 万文件规模，架构由三个关键决策决定：

1. **解码职责留在 Python（管道架构）**：`encoding_rs` 与 Python `gbk` codec 对非法字节的处理不一致，若让 Rust 直接解码 GBK 原始字节，结果必然与 Python 版分叉。因此固定为：Python 解码 → stdin 传 UTF-8 → Rust 只负责切章。零临时文件，与纯 Python 版逐字等价。

2. **批处理采用单进程常驻（`--serve`）**：逐文件启动 subprocess + 写临时文件，在 25 万文件规模下 I/O 与进程开销会成为瓶颈。`--serve` 单进程循环读帧，rayon 多核并行切章，流式输出 JSONL，进程只启动一次。

3. **编码判定用择优而非探测**：gb18030 是稠密映射、几乎对任何字节都能解码成功，规则式探测会产生「conf=1.0 但实际乱码」的假高置信。改为对 utf-8/gb18030/big5 三种解码结果比较全角标点密度，正确编码的标点密度通常比错误编码高两个数量级以上。

**几条设计原则**：

- **解码与切章职责分离**：解码由 Python 承担，容错行为以 Python codec 为唯一基准；Rust 不接触原始字节。跨语言边界不引入第二套解码行为，保证与纯 Python 版一致。
- **目录层级由数据统计决定**：不预设「卷>部>篇>集>章」的固定优先级，而是统计各候选标题单位的出现次数——出现少的是容器层（卷/部/篇），出现多的是章节层。
- **解析内核为纯函数、无共享状态**：单向数据流、无环依赖、输出确定，这是并行切分后结果可正确合并的前提；内核与编排层解耦，未来替换为原生实现时上层代码无需改动。
- **改动以等价性验证为准**：验收标准为章数、标题序列、按偏移读回正文三者逐字一致；验证顺序固定为受控小样本 → 单本端到端 → 小批量 parity → 全量。

性能基准（release 构建，31 本 / 7595 章 / 181MB UTF-8）：serve 批量 **5.83s**、逐文件 pipe **12.15s**。

## 踩坑记录（精华）

1. **Rust 解码 API 用错**：`decode_to_str` 接收固定长度缓冲，往空缓冲写 → 解码永远空串。须用 `decode_to_string`。
2. **raw_offsets 方案废弃**：Rust 直接解原始字节，因编码器与 Python codec 分歧导致章数错乱（同一文本 raw 切 3 章 / legacy 切 10 章），且不可小修消除 → 转向管道方案。
3. **编码探测假高置信**：真 utf-8 带聚集坏字节被误判 gb18030 conf=1.0，整本解成乱码 → 换择优范式。
4. **GUI 接入遗漏**：编码检测模块写好了但 GUI 从未调用，仍默认 utf-8 硬解。教训：新功能必须检查「调用方有没有真的接上」。
5. **chapters_subset 形状错**：把 index 条目（start/end/title）当 manifest 形状传给打包函数 → `KeyError: 'file'`。契约本是 manifest 形状，错的是调用方。
6. **部署用错构建**：误把 debug 构建（36MB）当 release 部署，慢 4.5~5.8×；release 构建仅 5.2MB。部署前须核对 exe 大小。
7. **工程纪律**：长任务主动分节点汇报进度；先小样本确定性验证再上全量；验证结论够用时立即收口，别兜圈子。

## 文件结构

| 文件 | 说明 |
|------|------|
| `txt_to_epub_gui_2.py` | GUI 主程序（入口） |
| `txt_to_epub_core.py` | 转换内核（切章 / 打包 / 管道与批处理接入） |
| `parse_txt_rust.exe` | 预编译 Rust 内核（release 构建，无需 Rust 环境） |
| `rust/` | Rust 内核源码（`cargo build --release` 可自行编译） |
| `exportTxtTocRule..json` | 章节识别规则集（**文件名是两个点**，须与脚本同目录） |

章节切分由 `exportTxtTocRule..json` 中的正则规则驱动（内置通用 / 晋江等多组规则按优先级匹配），可按需增删自定义。

## 常见问题

- **界面起不来**：需桌面图形环境，按提示 `pip install EbookLib Pillow tkinterdnd2`
- **章节识别不对**：检查规则文件是否与脚本同目录
- **编码乱码**：预览里手动切到正确编码（常见 utf-8 / gbk）再转换
- **Rust 引擎未找到**：检查 `parse_txt_rust.exe` 是否与脚本同目录、是否被杀毒软件隔离

## pure-python-beta 探索分支（纯 Python 全局调度器）

`pure-python-beta` 是一次方向性复盘产物：真实场景（海量 10MB 级小说、16–32 核、内存充足、任务粒度=整文件）下，Rust 加速的优势全部落空——瓶颈是进程启动与串行喂数据，而非单节点解码速度。用户理想模型（不成环的数据线、任意切分、编码分链、核数=进程数、动态资源分配）**纯 Python 100% 可实现**，不需要 Rust。

- **基底**：从 main 分出，用 v1.0.0 纯 Python 引擎替换 `core.py`/`gui_2.py` 的 Rust 委派，保留 main 上的纯 Python 有益探索（`encoding_detect.py` 编码择优、`hierarchy_rules.py` 分层目录），零 Rust 引用。
- **新增 `global_scheduler/` 包**（纯 Python）：预扫分链 + 全局进程池常驻 + 跨文件任务队列 + 动态收集；任务单元传引用（路径+行号），正文不跨进程。
- **验证**：89 本真实小说全量，89/89 成功、0 失败；编码分链实证 3 条链（utf-8 / utf-8-sig / gb18030）；与原版逐章 parity 一致。
- **核心教训**：① 非瓶颈上不发力——加速最不卡的一环是方向错误；② 报开销必带摊销方案（进程池常驻即可摊薄启动税，无需 Rust）；③ "多线程"= threading（GIL 锁死）+ multiprocessing（真并行），两者混为一谈会把人带进死胡同。
- 该分支暂不并入 main，作为独立探索保留。
