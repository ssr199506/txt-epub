# TXT → EPUB 转换工具

把纯文本小说（TXT）批量转换为 EPUB 电子书的桌面工具：自动识别章节、编码检测、章节排序、封面裁剪。内核为纯 Python，批量场景由 `global_scheduler` 进程池并行调度。

已实测 3GB 规模文本数据（大文件、多文件均有覆盖），性能优良；预估 10GB 左右规模平均性能不受影响（架构可线性外推）；更远量级受内存约束，需升级架构。

## 功能

- **TXT → EPUB**：正则规则自动识别章节标题并切分正文
- **批量处理**：进程池并行，`python -m global_scheduler.cli`
- **编码检测与预览**：utf-8 / gb18030 / big5 择优判定，可手动覆盖；转换前预览前 800 字
- **章节预览与排序**：列出识别出的章节，支持拖拽调整顺序
- **封面支持**：可选图片封面 + 裁剪预览
- **嵌套目录**：按「卷/部/篇/集 → 章」自动生成层级 TOC
- **大文件自适应分段**：按「甜点区」分段（默认约 256MB/段，`GS_SWEET_SPOT_MB` 可调），大文件多段并行，多文件按空闲 worker 排队

## 快速开始

```bash
pip install EbookLib Pillow tkinterdnd2
python txt_to_epub_gui_2.py    # 或双击 run_gui.bat 一键启动
```

需要桌面图形环境（Tk）。GUI 启动时会自动检查缺失依赖并尝试安装。

使用流程：选择/拖入 TXT → 确认编码（自动检测，乱码可手动改）→ 检查章节（可拖拽排序）→（可选）加封面 → 转换生成 `.epub`。

## 设计思路

以下决策基于 3GB 规模真实文本的验证：

1. **解码职责留在 Python**：`txt_to_epub_core._parse_chunk` 用 Python codec 解码并切章，跨进程只传引用（路径 + 行号），正文不跨进程搬运；容错行为以 Python codec 为唯一基准。
2. **进程池常驻 + 跨文件全局队列**：进程池只起一次，所有文件的任务混进一个全局队列，空闲 worker 自动取下一个任务；默认按 `os.cpu_count()` 起进程数，`GS_WORKER_CAP`（默认 32）作内存护栏。
3. **编码判定用择优而非探测**：gb18030 几乎对任何字节都能解码，规则式探测会产生假高置信。改为比较 utf-8/gb18030/big5 三种解码结果的全角标点密度，正确编码通常高两个数量级以上；并按编码分链调度。

设计原则：

- **解码与切章职责分离**：跨进程边界不引入第二套解码行为。
- **目录层级由数据统计决定**：按候选标题单位出现次数区分容器层（卷/部/篇）与章节层，不预设固定优先级。
- **解析内核为纯函数、无共享状态**：单向数据流、无环依赖、输出确定，是并行切分后正确合并的前提。
- **改动以等价性验证为准**：验收标准为章数、标题序列、按偏移读回正文三者逐字一致；验证顺序为小样本 → 单本端到端 → 小批量 parity → 全量。

验证：89 本真实小说全量通过（89/89），编码分链 3 条（utf-8 / utf-8-sig / gb18030），与原版逐章 parity 一致。

## 踩坑记录

1. **编码探测假高置信**：真 utf-8 带聚集坏字节被误判 gb18030，整本乱码 → 换择优范式。
2. **GUI 接入遗漏**：编码检测模块写了但 GUI 未调用，仍默认 utf-8 硬解。新功能必须检查调用方是否真的接上。
3. **chapters_subset 形状错**：把 index 条目当 manifest 形状传给打包函数 → `KeyError: 'file'`。契约本是 manifest 形状，错的是调用方。
4. **工程纪律**：长任务分节点汇报进度；先小样本确定性验证再上全量；结论够用立即收口。

## 文件结构

| 文件 | 说明 |
|------|------|
| `txt_to_epub_gui_2.py` | GUI 主程序（入口） |
| `txt_to_epub_core.py` | 转换内核（切章 / 打包 / 调度接入） |
| `global_scheduler/` | 纯 Python 批量调度包（预扫分链 + 进程池常驻 + 跨文件任务队列） |
| `encoding_detect.py` | 编码择优（全角标点密度比较） |
| `hierarchy_rules.py` | 分层目录规则（按出现频次统计容器层 / 章节层） |
| `exportTxtTocRule..json` | 章节识别规则集（**文件名是两个点**，须与脚本同目录） |

章节切分由 `exportTxtTocRule..json` 中的正则规则驱动，可按需增删自定义。

## 常见问题

- **界面起不来**：需桌面图形环境，按提示 `pip install EbookLib Pillow tkinterdnd2`
- **章节识别不对**：检查规则文件是否与脚本同目录
- **编码乱码**：预览里手动切到正确编码（常见 utf-8 / gbk）再转换

## 为什么是纯 Python

早期 `2.0 Beta` 用 Rust 解析内核加速，但真实场景（单本 10MB 级、16–32 核、任务粒度=整文件）下加速优势落空——瓶颈是进程启动与串行喂数据，而非解码速度。目标模型（不成环的数据线、任意切分、编码分链、核数=进程数、动态资源分配）纯 Python 100% 可实现，故 `v3.0.0` 以 `global_scheduler`（纯 Python 进程池）实现，零 Rust 依赖。

教训：① 非瓶颈上不发力；② 报开销必带摊销方案（进程池常驻摊薄启动税）；③ "多线程"是 threading（GIL 锁死）与 multiprocessing（真并行），二者混为一谈会把人带进死胡同。
