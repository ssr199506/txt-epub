# TXT → EPUB 转换工具

一个把纯文本小说（TXT）转换成 EPUB 电子书的桌面小工具：自动按章节切分、批量处理、编码自动检测、章节拖拽排序、封面裁剪。转换内核为纯 Python；批量场景由 `global_scheduler` 包调度——进程池常驻、跨文件任务队列、按 CPU 核数并行。

已在 **3GB 规模的文本数据**上通过测试、表现稳定。架构按文件级并行（单 worker 仅持有单个文件、数据按文件分批调度），**无论文件数量多还是单文件体积大都能处理**——绝对数量不是瓶颈，瓶颈只是墙钟时间；预计 10GB 以内规模可稳定运行（未实测，凭架构推断）。远期探索面向 845 GB / 25 万文件级别的小说库批处理，该规模仍是规划中、待验证的部分。


## 功能

- **TXT → EPUB**：正则规则自动识别章节标题并切分正文
- **批量处理**：一次多本连续转换，由 `global_scheduler` 进程池并行调度（`python -m global_scheduler.cli`）
- **编码自动检测**：拖入即自动判定 utf-8 / gb18030 / big5（择优范式），可手动覆盖
- **编码实时预览**：转换前预览前 800 字，避免乱码
- **章节预览与排序**：列出识别出的章节，支持拖拽调整顺序
- **封面支持**：可选图片封面 + 裁剪预览
- **嵌套目录**：按「卷/部/篇/集 → 章」自动生成层级 TOC，O(n) 复杂度
- **纯 Python 内核 + 进程池并行**：切章由纯 Python 承担，批量由 `global_scheduler` 按 CPU 核数起进程池，无 Rust 依赖
- **大文件 / 多文件都吃得下**：文件级并行调度，单文件体积大或文件数量多都能处理，绝对数量不是瓶颈

## 快速开始

```bash
pip install EbookLib Pillow tkinterdnd2
python txt_to_epub_gui_2.py    # 或双击 run_gui.bat 一键启动
```

需要桌面图形环境（Tk）。GUI 启动时会自动检查缺失依赖并尝试安装。

使用流程：选择/拖入 TXT → 确认编码（自动检测，乱码可手动改）→ 检查章节（可拖拽排序）→（可选）加封面 → 转换生成 `.epub`。

## 设计思路

当前版本内核为纯 Python，批量调度由 `global_scheduler` 承担；以下决策是在「3GB 规模真实文本」已验证的基础上做的。架构按文件级并行，**无论文件数量多还是单文件体积大都能处理**，绝对数量不是瓶颈；预计 10 GB 内规模可稳定运行（未实测，凭架构推断）。面向更大规模（如 845 GB / 25 万文件级别）的批处理目前仍在迭代中，未在该量级实测。核心决策：

1. **解码职责留在 Python（纯函数内核）**：`txt_to_epub_core._parse_chunk` 用 Python codec 解码并切章，跨进程只传引用（路径 + 行号），正文不跨进程搬运。容错行为以 Python codec 为唯一基准，天然与纯 Python 版一致。

2. **进程池常驻 + 跨文件全局队列**：进程池只起一次，所有文件的任务混合进一个全局队列，空闲 worker 自动取下一个——短文件跑完即释放 worker 去切长文件，天然实现动态资源分配。`global_scheduler` 默认按 `os.cpu_count()` 起进程数，并用 `GS_WORKER_CAP`（默认 32）做内存护栏。

3. **编码判定用择优而非探测**：gb18030 是稠密映射、几乎对任何字节都能解码成功，规则式探测会产生「conf=1.0 但实际乱码」的假高置信。改为对 utf-8/gb18030/big5 三种解码结果比较全角标点密度，正确编码的标点密度通常比错误编码高两个数量级以上；并按编码把文件归入不同「链」，链内按 size 降序调度。

**几条设计原则**：

- **解码与切章职责分离**：解码由 Python 承担，容错行为以 Python codec 为唯一基准；跨进程边界不引入第二套解码行为。
- **目录层级由数据统计决定**：不预设「卷>部>篇>集>章」的固定优先级，而是统计各候选标题单位的出现次数——出现少的是容器层（卷/部/篇），出现多的是章节层。
- **解析内核为纯函数、无共享状态**：单向数据流、无环依赖、输出确定，是并行切分后结果可正确合并的前提；内核与编排层解耦。
- **改动以等价性验证为准**：验收标准为章数、标题序列、按偏移读回正文三者逐字一致；验证顺序固定为受控小样本 → 单本端到端 → 小批量 parity → 全量。

验证（89 本真实小说全量）：89/89 成功、0 失败；编码分链实证 3 条链（utf-8 / utf-8-sig / gb18030）；与原版逐章 parity 一致。

## 踩坑记录（精华）

1. **编码探测假高置信**：真 utf-8 带聚集坏字节被误判 gb18030 conf=1.0，整本解成乱码 → 换择优范式。
2. **GUI 接入遗漏**：编码检测模块写好了但 GUI 从未调用，仍默认 utf-8 硬解。教训：新功能必须检查「调用方有没有真的接上」。
3. **chapters_subset 形状错**：把 index 条目（start/end/title）当 manifest 形状传给打包函数 → `KeyError: 'file'`。契约本是 manifest 形状，错的是调用方。
4. **工程纪律**：长任务主动分节点汇报进度；先小样本确定性验证再上全量；验证结论够用时立即收口，别兜圈子。

## 文件结构

| 文件 | 说明 |
|------|------|
| `txt_to_epub_gui_2.py` | GUI 主程序（入口） |
| `txt_to_epub_core.py` | 转换内核（切章 / 打包 / 全局调度接入） |
| `global_scheduler/` | 纯 Python 批量调度包（预扫分链 + 进程池常驻 + 跨文件任务队列） |
| `encoding_detect.py` | 编码择优（utf-8 / gb18030 / big5 全角标点密度比较） |
| `hierarchy_rules.py` | 分层目录规则（按出现频次统计容器层 / 章节层） |
| `exportTxtTocRule..json` | 章节识别规则集（**文件名是两个点**，须与脚本同目录） |

章节切分由 `exportTxtTocRule..json` 中的正则规则驱动（内置通用 / 晋江等多组规则按优先级匹配），可按需增删自定义。

## 常见问题

- **界面起不来**：需桌面图形环境，按提示 `pip install EbookLib Pillow tkinterdnd2`
- **章节识别不对**：检查规则文件是否与脚本同目录
- **编码乱码**：预览里手动切到正确编码（常见 utf-8 / gbk）再转换

## 为什么是纯 Python（移除 Rust 的复盘）

早期 `2.0 Beta` 尝试用 Rust 解析内核加速，但在真实场景（单本可达 10MB 级的小说、16–32 核、内存充足、任务粒度=整文件）下加速优势全部落空——瓶颈是进程启动与串行喂数据，而非单节点解码速度。用户理想模型（不成环的数据线、任意切分、编码分链、核数=进程数、动态资源分配）**纯 Python 100% 可实现**，故当前 `v3.0.0` 以 `global_scheduler` 包（纯 Python 进程池）实现，零 Rust 依赖。

核心教训：① 非瓶颈上不发力——加速最不卡的一环是方向错误；② 报开销必带摊销方案（进程池常驻即可摊薄启动税，无需 Rust）；③ "多线程"= threading（GIL 锁死）+ multiprocessing（真并行），两者混为一谈会把人带进死胡同。
